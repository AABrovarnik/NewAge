# Review Notes — AI Secretary v1.0 Dev Pack

Разбор исходного пакета постановки задачи (`original/`) и версия с правками (`reviewed/`).

## Внесённые правки

### 1. `metadata` как имя колонки конфликтует с SQLAlchemy 2.x

Во всех таблицах (`tasks`, `source_messages`, `task_events`, `reminders`,
`user_settings`, `integration_accounts`) была колонка `metadata JSONB`.
В SQLAlchemy Declarative `Base.metadata` зарезервировано под объект
`MetaData` — модель с атрибутом `metadata: Mapped[dict] = mapped_column(...)`
падает с `InvalidRequestError` при импорте.

**Правка:** в `DATABASE_SCHEMA.md` добавлено явное указание маппить
SQL-колонку `metadata` на другое имя атрибута ORM, например:

```python
extra: Mapped[dict] = mapped_column("metadata", JSONB, nullable=False, default=dict)
```

SQL-схема (имя колонки в БД) не менялась — конфликт чисто на уровне Python/ORM.

### 2. Двусмысленность `WAITING` (task_type vs status)

`WAITING` использовалось одновременно как значение `task_type`
("я жду ответа от кого-то") и как значение `status`
("задача приостановлена/заблокирована"). При этом MASTER_PROMPT.md
явно требовал "не смешивай эти сущности" — но одинаковое имя в двух
разных enum'ах создавало риск ошибок и в коде, и в промптах LLM
(Classifier тоже возвращал `WAITING`).

**Правка:** значение `task_type` переименовано в `AWAITING` во всех
документах (`README.md`, `MASTER_PROMPT.md`, `PROMPTS.md`, `API.md`,
`IMPLEMENTATION_PLAN.md`, `DATABASE_SCHEMA.md`). `status.WAITING`
оставлен без изменений — это другая сущность.

### 3. Отсутствовал переход `NEW -> WAITING` в state machine

Сценарий "Жду договор от Ивана завтра" (`task_type=AWAITING`) обычно
сразу создаёт задачу в статусе `WAITING`, минуя `PLANNED`/`IN_PROGRESS`,
но такого перехода не было в списке допустимых.

**Правка:** добавлен `NEW -> WAITING` в `DATABASE_SCHEMA.md` с пояснением.

### 4. `Europe/Moscow` как дефолт часового пояса

`.env.example` и DEFAULT в `users.timezone` были жёстко заданы как
`Europe/Moscow` — тихая ловушка для пользователя из другого региона.

**Правка:** дефолт БД изменён на нейтральный `UTC` с пояснением, что
это fallback до онбординга, а не рекомендуемое значение; в
`.env.example` добавлен комментарий, что `TIMEZONE` — это системная
переменная (для scheduler/digest), а часовой пояс конкретного
пользователя должен запрашиваться отдельно и храниться в `users.timezone`.

## Что не менялось

Архитектура (`ARCHITECTURE.md`), API-контракты (`API.md`, кроме
переименования `WAITING`→`AWAITING` в двух местах), docker-compose,
политика подтверждений, reminder policy, confidence policy — всё это
показалось последовательным и продуманным, правок не потребовалось.

## Рекомендации по дополнительной проверке ТЗ

Отдельного "совета директоров" как инструмента у меня нет, но для
документа такого объёма и с доступом к Gmail/Calendar имеет смысл
несколько независимых проходов с разным фокусом, прежде чем отдавать
агенту в разработку:

1. **Security/privacy review** — отдельно посмотреть на обработку
   персональных данных (письма, контакты третьих лиц), шифрование
   OAuth-токенов, ретеншн `source_messages` с чужими email. Учитывая
   Gmail-интеграцию, стоит явно решить вопрос хранения/удаления
   писем третьих лиц (GDPR-подобные требования, даже если для
   личного использования).
2. **Red-team на prompt injection** — документ уже требует "внешний
   текст = данные", но стоит явно прогнать несколько adversarial
   примеров писем/сообщений через будущий Classifier/Extractor до
   продакшена, а не полагаться только на системный промпт.
3. **Operational review** — тестовое восстановление backup на чистой
   БД (это уже есть в плане, но стоит реально прогнать перед
   Phase 11), проверка поведения при недоступности LLM/Gmail/Calendar
   под нагрузкой, а не только "по спецификации".
4. **Постепенный rollout вместо одного большого прогона** — то, что
   уже заложено в IMPLEMENTATION_PLAN.md (фазы с acceptance criteria)
   — это и есть правильная практика; важно реально останавливаться
   на красных тестах, а не просить агента "продолжай, разберёмся
   потом".
5. **Второй независимый агент/сессия ревьюит diff каждой фазы** —
   дешёвый способ получить "второе мнение" без формального совета:
   после каждой фазы просить отдельную сессию Claude Code (без
   контекста реализации) провести code review по критериям из
   MASTER_PROMPT.md.

Ничего из этого не блокирует старт — это скорее чек-лист, который
стоит держать в IMPLEMENTATION_PLAN.md как часть Phase 9/10.
